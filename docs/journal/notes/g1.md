# Notes: g1

Version: g1 (gate G1: the human looks at the 3D model and its parts), work from 2026-10-20 to 2026-10-22. Source docs are in Vietnamese; every beat is self-contained. Decision codes like 9.5 are `docs/decisions/` entries; L-004 is an entry in `docs/harness/lessons.md`. Commit hashes are 7 characters.

Setup: Claude (main session) coordinates; sub-agents implement in separate git worktrees; separate reviewer agents check each task and then the whole branch. The target is a four-legged spider robot built from simple shapes in Blender and simulated in MuJoCo.

## Beat: A reviewer-proposed servo feature turned out not to exist

- **Type:** agent-problem
- **What happened:** During design step 9, two review sub-agents read the plan. One suggested modelling the servos with a MuJoCo actuator type called `pid` with a `slewmax` option (a built-in speed limit on the command). It sounded right and fitted the plan. Before accepting it, Claude checked each new-sounding MuJoCo feature the reviewers named against MuJoCo's official changelog. The `dcmotor` actuator (3.7.0), reflected damping and armature (3.7.0) and command delay (3.5.0) were real. `pid` with `slewmax` could not be found in the changelog or the XML reference at all.
- **How it was solved:** The suggestion was removed from decision 9.1. Servo speed limiting stays in the controller code; the servo model uses the standard `position` actuator with force limits, with `dcmotor` as a documented upgrade path. The same review corrected other confident claims, for example that `mjpython` is required only for one viewer call, not all of them. Takeaway: a plausible technical claim from an agent reviewer counts only after it is checked against the primary source. Evidence note: this is a review of the plan, not of code, so no commit fixes it; the correction is in decision 9.1 and the table at the top of step 9.
- **Evidence:** step 9 review (table of checked features), 9.1; commit ef2aea5 (log including step 9)
- **Media:** none

## Beat: The torso was thinned to fit the weight budget

- **Type:** idea
- **What happened:** Decision 9.5 set a mass budget for the first model: 250 to 350 g, because tiny hobby servos have little torque and the static torque check must stay under 50 percent of each servo's maximum. The implementer of the model-building task built the torso as a 35 mm thick block, the plan's starting size. The result was 417 g against the 350 g limit, and the budget test failed; the solid 35 mm torso alone was 122 g. The test was not skipped and the limit was not raised.
- **How it was solved:** Project rule 2 says change dimensions before servos and never loosen the 50 percent margin. The coordinator ruled the torso should be a flat 10 mm plate, which also matches the reference photo (two thin plates with a battery holder on top). Density, fill, servos and battery mass stayed unchanged. Total mass fell to 330.3 g, inside the budget (the G1 parts table lists every body). The G1 README notes its own risk: a plate this thin may be too weak for a real battery mount, to be revisited at the G1 review. The G1 review revisited much more than that (see the payload beat). Evidence note: the README states the 417 g and 122 g figures and the new total; a per-part breakdown of the failing build is not in the public record.
- **Evidence:** 9.5, 14.5 (never loosen the 50% margin); docs/reference/g1/README.md (parts table, 417 g vs 330.3 g); commits c3357e4 (model export and build), c121e68 (thin torso plate), d039e47 (plan updated: torso 0.010 m)
- **Media:** none

## Beat: Every task review said Approved, yet the camera angles were wrong

- **Type:** agent-problem
- **What happened:** The G1 work was split into six tasks, each reviewed by a separate reviewer agent against that task's diff, and every one said Approved. A final review of the whole branch (commits d37c7b5 to 17cf137) then found three important problems. First, the MuJoCo snapshot cameras did not match the Blender cameras. The MuJoCo view angles were set to different sides than Blender's: the fix commit says the MuJoCo views must put front at plus-x, side at plus-y and iso at (+1,+1,+1), the same sides as the Blender render script, and it changed the camera azimuths to do so (the old and new values are in the `VIEWS` line of that commit). Second, no test ever ran on the committed `models/spider.blend`; all tests built a fresh model in a temp folder. Third, a torque risk was invisible at G1 (it came back in the payload beat). The cause: the Blender task and the MuJoCo snapshot task each followed their own brief, and the convention linking them, which side is "front", was in no brief. Each reviewer saw one diff only, so nobody compared the two.
- **How it was solved:** Camera angles were corrected, with tests that measure the rendered camera position against Blender's view directions, plus a test that the four images differ pairwise (c8d0d6e); a test now exports the committed Blender file and checks mass budget and feet positions (f68560d). Lesson L-004 records the process change: when a task reuses a convention from an earlier task (view direction, key names, units), copy that convention into the brief, and make the final review check the seams between tasks explicitly. L-004 is not yet a standing rule (that needs the human's approval).
- **Evidence:** L-004; commits c8d0d6e, f68560d, 17cf137 (the task under review), 30f58c0 (lesson L-004 added)
- **Media:** none

## Beat: The final review produced a batch of fixes, each a quiet failure the tests had not seen

- **Type:** agent-problem
- **What happened:** The whole-branch review also triaged minor issues that earlier reviews had deferred as "later, nothing depends on it". They were fixed in one wave before the G1 gate, so the G1 images would not need re-rendering twice. What the items had in common is that each was a way for the system to fail quietly:
  - A scale check read only an object's `scale`, so a Blender object resized through `delta_scale` slipped past validation (abaea81).
  - Config accepted zero or negative values, so a zero position-error setting would crash with a division by zero far from the cause; it now raises an error naming the field, and a missing servo field names the servo (7a05354).
  - Export wrote straight into the output folder, so a failed export or a renamed object left stale or half-written files; it now writes into a temporary sibling folder and swaps it in (52975d8).
  - Floor contact used the last foot's radius instead of each foot's own (1f40ed1).
  - The model builder could not tell that `build/model` was older than `models/spider.blend`, and default paths depended on the current directory; it now compares a stored hash and anchors paths to the repo root (6d4f46e).
  - The tests compared actuator names against the same list the code used, which proves nothing; new tests assert real gains, ranges, joint parameters and foot contact from the config (3f94df1).
  - A hung Blender would hang the agent forever, and a wrong `BLENDER_BIN` silently fell through to another Blender; there is now a 300 s timeout (override with `BLENDER_TIMEOUT`) and structured JSON errors (bc472c0).
- **How it was solved:** All of the above, in commits tagged "(G1 final review)" (the camera fix c8d0d6e and test f68560d from the previous beat belong to the same wave).
- **Evidence:** L-004 (same final review); commits abaea81, 7a05354, 52975d8, 1f40ed1, 6d4f46e, 3f94df1, bc472c0
- **Media:** none

## Beat: The human looked at the robot and asked for it to carry 2 kg

- **Type:** human-problem
- **What happened:** At the G1 gate the user looked at the finished 330 g model in MuJoCo and found it not stable enough. They wanted the robot to carry a payload and made balance its main skill; the first figure was about 3 kg. This requirement existed nowhere in the earlier 18 decision steps, and it broke the weight budget and the servo choice G1 had just been built around. The robot was to stay like the reference photo (19.2, proposed by Claude, confirmed by the user).
- **How it was solved:** Instead of guessing, Claude ran a sub-agent probe in simulation (the project's "propose, probe, compose" method) on three leg layouts: A long and splayed, B short and splayed, C long and tucked. At 3 kg none of the three failed the static torque check (50 percent of servo maximum). At 2 kg, layout B with a stronger hip servo passed (table in decision step 19). The user chose 2 kg, and Claude recommended layout B with a 40 kg·cm servo at the hip pitch joint, bringing the worst joint to 0.45 (decisions 19.1 to 19.8). Nobody lowered the 50 percent margin. The probe also exposed two real model bugs: foot friction had no effect (the floor's default friction of 1.0 wins because MuJoCo takes the larger value), and feet crept sideways under steady push because of contact solver settings. Both must be fixed with a regression test before the gate passes (19.9, BUG-001 and BUG-002). Thin evidence: the probe numbers use estimated servo specs, which decision 19.4 itself flags as estimates until a datasheet or a measured servo exists.
- **Evidence:** 19.1 to 19.10, 9.5 (old 250 to 350 g budget, replaced by 19.7 and 19.8), BUG-001, BUG-002; commits d8dd4c1 (decisions step 19, including the probe results table), 6117c5f (G1 revision plan)
